Type of document: build brief (project task, "Forms: Your Richest Unit")

In one sentence:
This brief has you direct Claude to build a fully labeled, grouped, validated registration form for your site, plus a deliberately lazy copy for the AudioLab comparison.

Main ideas:
The brief pairs with html08 (HTML Forms). It says forms are where screen reader support is either professional or garbage, with nothing in between, and that forms-mode auditing is the sharpest audit skill in the track.
1. What to build: a real registration form for your site, with a purpose that fits your topic.
- Three fieldset groups, each with a legend, for example Contact Info, Preferences, and Confirmation.
- Inputs that cover text, email, a radio group of 3 or more options, checkboxes (3 or more), a select dropdown, and a textarea.
- Every input labeled with a label element connected by for and id.
- Sensible required fields, and one field checked with pattern (a phone number or ZIP code).
- A submit button whose text says something better than "Submit."
- Styling from your stylesheet, including visible focus styles (input:focus), because every keyboard user needs a visible marker of where focus is.
2. The must-say list:
- form, action, and GET versus POST, including which one to use for form submissions with personal data and why.
- label with for matching the input's id. Say the mechanism, not just "add labels."
- fieldset and legend, and what a legend does for a radio group specifically.
- input type values by name, required, and pattern.
- tabindex, and why the answer is almost always "don't set it; fix the source order instead."
3. The twist: have Claude build the same form a second time, badly, as lazy-form.html, with no labels (placeholders only), no fieldsets, and a generic button. The AudioLab runs both. Delete the lazy version afterward and do not commit it.

Code: <label for="email">Email address</label> <input type="email" id="email" required>
The label's for value matches the input's id, which connects them, so a screen reader announces "Email address" when you land on the field. The required attribute makes the browser block an empty submit. (Example written for these notes.)

Key terms:
form — the element wrapping all the controls of a form.
action — the attribute giving the address the form's data is sent to.
GET and POST — the two methods for sending form data; the brief asks which suits personal data.
label — text naming a control, connected by for and id.
for and id — the matching pair that links a label to its input.
fieldset — a group of related controls.
legend — the title of a fieldset.
input type — values such as text, email, radio, and checkbox that set what kind of control an input is.
Radio group — a set of options where only one can be chosen.
Checkbox — an option that can be turned on or off independently.
select — a dropdown list.
textarea — a multi-line text box.
required — makes a field mandatory.
pattern — checks a field's value against a format.
input:focus — a CSS selector for styling the field that currently has keyboard focus.
tabindex — an attribute that changes Tab order; the brief says to almost never set it.
Placeholder — hint text inside a field, used instead of labels in the lazy version.

What you are asked to do:
- Direct Claude to build the registration form with all listed parts, including three fieldsets with legends, every required input type, connected labels, required and pattern fields, a descriptive submit button, and visible focus styles.
- Use every must-say term by name and explain the for and id mechanism.
- Have Claude build lazy-form.html for the AudioLab, then delete it without committing.
- Commit: the real form live on your site, ai08_PromptLog.md, and your completed ConceptCheck and AudioLab.

Watch out for:
- Placeholders are not labels.
- Do not use tabindex to fix Tab order; fix the source order.
- A submit button that just says "Submit" does not meet the brief.
