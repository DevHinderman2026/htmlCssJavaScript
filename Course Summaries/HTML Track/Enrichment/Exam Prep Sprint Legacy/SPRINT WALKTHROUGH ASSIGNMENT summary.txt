Summary of: SPRINT_WALKTHROUGH_ASSIGNMENT.md
Course: HTML CSS JavaScript track
Lesson: Exam Prep Sprint Legacy
Type of document: project (team teaching assignment)

In one sentence:
This assignment puts students in teams that each write a follow-along markdown walkthrough on one exam topic and then teach it live to the class from Mr. McMaster's computer.

Main ideas:
1. The big idea: you teach the class. Each team writes a step-by-step "build this with me" guide that everyone types along with in VS Code while the team presents. It should be simple, clear, and introductory, with many small code chunks, lots of explanation, and no assumption that classmates already know the topic.
2. Teams and topics:
- Team 1, 3 students: Bootstrap Basics, folder sprint01_bootstrap.
- Team 2, 3 students: HTML Forms and Validation, folder sprint02_forms.
- Team 3, 3 students: SEO, Accessibility and Deployment, folder sprint03_seoDeployment.
- Team 4, 4 students: Troubleshooting, QA and Dev Tools, folder sprint04_troubleshootingQA.
3. Splitting the work in a 3-person team: Person A writes the first 1 to 2 mini-walkthroughs and tests the code in a browser; Person B writes the next 1 to 2 and tests them; Person C is Editor and Presenter Lead, writing the intro and summary, merging A and B's work into one clean, consistent file, and leading the presentation.
4. Splitting the work in the 4-person team: Person A writes 1 to 2 walkthroughs on finding and fixing bugs with DevTools; Person B writes 1 to 2 on validation, cross-browser testing, and test cases; Person C writes 1 on scoping a project and creating a brief; Person D is Editor and Presenter Lead.
5. Everyone reviews the final file before presentation day. If the code does not work, the walkthrough fails.
6. What makes a good walkthrough (modeled on the course files html08_Walkthrough.md and html11_Walkthrough.md): start from a blank file and build piece by piece; give the exact code to type; explain each piece in plain English; keep each step small, never 50 lines at once; include fill-in-the-blank spots where students finish something themselves. The test: a classmate who has never seen the topic can follow it and end up with a working example.
7. Presentation day: the team comes to Mr. McMaster's projected computer, opens the walkthrough, and types and explains step by step while everyone follows on their own machines. Each team gets about 20 to 25 minutes, and the class should have working examples at the end. Tips: go slower than you think; check that everyone has caught up after each chunk; treat anything that breaks as a teaching moment (that is what Sprint 04 is about); have one teammate watch the class to catch anyone falling behind.
8. Team 1 guide, Bootstrap Basics. Focus on the grid and a few components. Walkthrough 1: add the Bootstrap CDN link to an HTML file, build a 2-column layout with container, row, and col, compare col-md-6 with col-lg-4 at different sizes, and have the class resize the browser. Walkthrough 2: a navbar with a brand name and 3 links, showing the hamburger at mobile width and explaining navbar-expand-lg, navbar-dark, and bg-dark. Walkthrough 3: three cards in a row (image, title, text, button), button styles such as btn-primary and btn-outline-secondary, and spacing utility classes mt-3, p-4, and text-center. Vocabulary: Bootstrap, CDN, container, row, col, grid system, breakpoint, responsive design, navbar, card, utility class. Resources: the official Bootstrap 5.3 Getting Started docs (the main resource), the W3Schools Bootstrap 5 tutorial, Net Ninja and Traversy Media Bootstrap 5 crash courses on YouTube, and the Bootstrap Examples page for inspiration only (do not copy).
9. Team 2 guide, HTML Forms and Validation. Walkthrough 1: a form tag (explain action and method), labeled text inputs for first name, last name, and email, the placeholder and required attributes, type email, and why label for matters for accessibility. Walkthrough 2: radio buttons for a single choice, checkboxes for multiple choices, a select dropdown with option elements, and why radio buttons share the same name attribute. Walkthrough 3: a textarea, fieldset and legend to group fields, submit and reset buttons, and basic CSS (width, padding, labels on their own lines). Vocabulary: form, action, method, GET, POST, input, type, label, for and id connection, placeholder, required, radio, checkbox, select, option, textarea, fieldset, legend, submit. Resources: MDN's HTML Forms guide (start with "Your first form" and "How to structure a form"), W3Schools HTML Forms, CS50 Web on YouTube (Brian Yu), Web Dev Simplified's 25-minute forms video, and MDN's input element reference.
10. Team 3 guide, SEO, Accessibility and Deployment (keep each part short and practical). Walkthrough 1, SEO: start with a page that has no title, no meta description, and generic headings; add a proper title, a meta description, correct h1 to h2 to h3 order, and alt text; explain why search engines care. Walkthrough 2, accessibility: improve the same page with alt text, color contrast checked with a contrast tool, an aria-label on a nav element, a look at the DevTools Accessibility tab to see what a screen reader gets, and keyboard navigation with tabindex and focus styles. Walkthrough 3, GitHub Pages: create a repo, use git add, git commit, and git push (or GitHub Desktop), enable Pages in settings, and show the live URL. Vocabulary: SEO, title tag, meta description, heading hierarchy, alt text, accessibility, ADA, WCAG, screen reader, color contrast, ARIA, HTTP and HTTPS, DNS, Git, GitHub Pages, static site. Resources: Google's SEO Starter Guide, WebAIM's Introduction to Accessibility, the GitHub Pages Quickstart, CS50 Web lectures, The Coding Train on GitHub Pages, the WebAIM Color Contrast Checker, MDN's Accessibility guide, and the W3Schools Git tutorial.
11. Team 4 guide, Troubleshooting, QA and Dev Tools (the most hands-on; break things on purpose and fix them live). Walkthrough 1: open DevTools with right-click and Inspect; the Elements panel for structure; the Styles panel to see and toggle CSS; live edits that do not save permanently. Walkthrough 2: a short file with 4 to 5 planted bugs (a missing closing tag, a broken image path, a CSS selector typo such as contaner instead of container, a link with the wrong href, a missing alt attribute), found with DevTools and the W3C Validator and fixed while explaining the thinking. Walkthrough 3: run a page through validator.w3.org and read the errors, compare the page in Chrome and Firefox, and use DevTools responsive mode. Walkthrough 4: what a test case looks like (for example, click Submit, expected result: form submits and shows confirmation), write 3 to 4 test cases for a simple form, and run them as a class. Vocabulary: troubleshooting, debugging, DevTools, Elements panel, Styles panel, Console, W3C Validator, cross-browser testing, test case, QA, bug report, root cause. Resources: the Chrome DevTools overview docs, the W3C Markup Validator, W3Schools on HTML validation, Chrome Developers and Traversy Media DevTools videos, the CS50 Web testing lecture, MDN on browser developer tools, and CSS-Tricks on debugging CSS.
12. General resource list: W3Schools, MDN Web Docs, Bootstrap docs, CS50 Web, The Odin Project, freeCodeCamp, WebAIM, the W3C Validator, Chrome DevTools docs, and GitHub Pages docs.

Key terms:
Walkthrough — a follow-along tutorial that builds a working example step by step.
Mini-walkthrough or chunk — one short, complete example inside the walkthrough.
CDN (content delivery network) — a server that hosts files like Bootstrap so you can link to them instead of downloading them.
Test case — a written check stating an action and its expected result.
QA (quality assurance) — the process of making sure a product works as intended.
Root cause — the underlying reason a bug happens.
Cross-browser testing — checking that a page works the same in different browsers.

What you are asked to do:
1. Deliverable: one markdown file per team, named sprint##_Walkthrough.md (with your sprint number), following WALKTHROUGH_TEMPLATE.md.
2. It must guide the class through 3 to 4 short walkthrough examples, followed in VS Code in real time.
3. Required contents: a 2 to 3 sentence intro (maximum) on what the topic is and why it matters; 3 to 4 mini-walkthroughs, each building a small example from scratch; every code chunk complete and copy-pasteable; plain-English explanations before and after every chunk ("Here's what we're doing" and "What just happened"); a "What to look for" note after each example; and a closing summary of the 5 to 6 most important things to remember for the exam.
4. Everyone on the team must review the final file, and all code must be tested in a browser.
5. Present live for about 20 to 25 minutes.
Timeline: Day 1, form teams, read the guide, claim a topic, start research. Day 2, research, write walkthroughs, test code. Day 3, combine, edit for clarity, practice presenting. Day 4, all four teams present.
Grading, 100 points total:
- Walkthrough file is complete and follows the template: 25 points.
- Code examples actually work when followed step by step: 25 points.
- Explanations are clear and helpful so a beginner could follow: 20 points.
- Live presentation is organized and the class can follow along: 20 points.
- Team collaboration, everyone contributed: 10 points.

Watch out for:
- Broken code is the biggest risk; the file fails if the code does not work.
- Do not dump big blocks of code; small steps with explanations are required.
- Keep the intro to 2 or 3 sentences.
- Heads up: there are five sprint folders but only four teams. Sprint 05 (exam review) has no team because it is the whole-class review at the end, so nobody writes a walkthrough for it.
- Correction: write 4 mini-walkthroughs, which satisfies both this assignment's "3 to 4" and the template's 4 required chunks (a 5th is optional).
