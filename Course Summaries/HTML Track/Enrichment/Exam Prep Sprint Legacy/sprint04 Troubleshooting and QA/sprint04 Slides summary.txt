Lesson: sprint04 Troubleshooting and QA
Type of document: slideshow

In one sentence:
An exam prep slideshow on four systematic troubleshooting methods, quality assurance and test cases, usability and acceptance testing, and project management basics such as scope, stakeholders, design briefs, milestones and the critical path.

Main ideas:
1. Why systematic troubleshooting matters. Random guessing wastes time and misses the real problem. A logical method finds it faster. The key principle: start with what you know, narrow down step by step, document what you find, and verify your fix works. This is Outcome 2.11, troubleshoot web applications using logical methods.
2. Method 1, Top-Down. Start with the big picture and narrow down. First ask whether the site loads at all; if not, check the server or hosting and the internet connection. If it loads, ask whether the specific page loads, then whether the specific element displays (if not, check the CSS and layout and the HTML structure), then whether the element works (if not, check the JavaScript logic). Best for general problems where "nothing works". Gives a fast first diagnosis.
3. Method 2, Bottom-Up. Start with the smallest details and work up: check the syntax (whether the HTML, CSS and JavaScript are valid), then the individual element, then the whole page (whether all elements work together), then the entire site (whether all pages work). Best for code-level problems and finding bugs. More thorough and catches small issues.
4. Method 3, Follow the Path. Trace the data flow from start to finish: the user clicks a button, the JavaScript event listener fires, the function runs (check its logic and variables), the page (DOM) updates (check the selectors and changes), and the element displays (check CSS and layout). Best for interactive features such as buttons and forms that do not work.
5. Method 4, Spot the Differences. Compare a working version with a broken one. Check what changed between versions, whether you edited the HTML, CSS or JavaScript, whether file paths are correct, whether IDs and classes match, and whether a selector has a typo. Best after a change broke something, or when comparing pages. Very fast if you know what changed.
6. When to use each: Top-Down when the whole site is broken (site will not load); Bottom-Up to find a specific bug (a button does not click); Follow the Path for interactive features (a form not submitting); Spot the Differences after changes (a navbar missing on one page). Pro tip: use Top-Down first to find the problem area, then switch methods for the details.
7. Quality assurance (QA) is formal, systematic testing before launch. It catches bugs before users do, makes sure features work, tests multiple browsers and devices, prevents bad experiences, and saves money because bugs cost more to fix later. QA is documented, organized and planned; "just testing" is random clicking. This is Outcome 2.12, conduct QA testing and create test cases.
8. A test case is a detailed instruction for testing one feature or scenario. The template has: Test ID (for example TC-001), Description (for example login with valid credentials), Steps (open login page, enter username, enter password, click Submit), Expected Result (user logged in and sent to the dashboard), Actual Result (what really happened), and Pass or Fail. Good test cases are clear and specific, repeatable (same steps give the same result), independent (do not depend on other tests), and documented for the team.
9. Usability testing means real users, not the developers, try the site. They do not know how it was built, find problems you missed, and think differently. User Acceptance Testing (UAT) is when the client or stakeholder signs off that the site meets their needs. The difference: QA checks that it works technically, usability checks that users can use it and like it, and UAT checks that it meets the business goals. Example: a site can calculate correctly (passes QA) while users cannot find the button (fails usability).
10. Acceptance criteria are the conditions that must be true for the project to be approved. Examples: loads in under 3 seconds; works in Chrome, Firefox, Safari and Edge; responsive from 320 to 2560 pixels wide; all forms submit without errors; the client can edit homepage content; passes WCAG accessibility standards. They give a clear finish line, set client expectations, prevent scope creep, and are the basis for test cases.
11. Project scope is what is included and not included. Included: number of pages, features (forms, search, shopping cart), design requirements, browser and device support, content. Not included: nice-to-have features, features for future updates, things beyond the budget, work outside the timeline. Scope prevents scope creep (the project growing bigger and bigger), sets clear expectations, keeps timelines and budgets realistic, and tells the team what to build.
12. Stakeholders are people invested in the project's success: the client or business owner, end users, the project manager, and the design and development team. The target audience is who will use the site: their age, location and tech level, what problems the site solves for them, and how they use it. Example: an e-commerce site for college students should be mobile-first with a simple checkout and a trendy design.
13. A design brief is a one-page summary of the whole project: project name and goal, target audience, scope, timeline, budget, and success metrics. Example: client Green Gardens Nursery; goal online plant sales and customer education; audience homeowners 25 to 65 and gardening fans; pages Home, Shop, Blog, Contact, About; timeline 6 weeks; budget 2,500 dollars.
14. Timeline, milestones and critical path. The timeline is start date, end date and major phases. Milestones are key checkpoints; the example is week 1 design approved, week 2 homepage coded, week 3 all pages coded, week 4 QA begins, week 5 client review and fixes, week 6 launch. The critical path is the longest chain of dependent tasks, which sets the minimum project time. Tasks on the critical path cannot be delayed or the project will be late. The example chain is client approval 3 days, design 5 days, development 10 days, QA 3 days, launch 1 day.
15. Key takeaways. Troubleshooting (Outcome 2.11): use logical methods, choose the right one, document findings. QA (Outcome 2.12): test with test cases, remember real users find different problems, get sign-off with acceptance criteria. Project management (Outcome 2.9): define what is and is not in scope, know the audience and stakeholders, break work into milestones, identify the critical path. Good planning prevents problems, good troubleshooting fixes them, and good QA catches them first.

Key terms:
Top-Down — troubleshooting from the big picture down to details.
Bottom-Up — troubleshooting from code details up to the whole site.
Follow the Path — tracing data from a user action through code to the display.
Spot the Differences — comparing a working version to a broken one.
DOM — the browser's live model of the page that JavaScript changes.
QA (quality assurance) — formal, documented testing before launch.
test case — step-by-step test of one feature with expected and actual results.
usability testing — real users trying the site.
UAT (user acceptance testing) — client sign-off that the site meets needs.
acceptance criteria — conditions that must be met for approval.
scope — what is and is not included.
scope creep — a project growing beyond its agreed scope.
stakeholder — anyone invested in the project's success.
target audience — the people the site is for.
design brief — one-page project summary.
milestone — key checkpoint in the timeline.
critical path — the longest sequence of dependent tasks; sets minimum duration.

Watch out for:
- Know which method fits which symptom; exam questions describe a symptom and ask for the best method.
- QA, usability testing and UAT are three different things.
- Scope must list what is NOT included as well as what is.
- Correction: the critical path example totals 22 days (3 + 5 + 10 + 3 + 1), because the whole longest chain of dependent tasks, including QA and launch, sets the minimum project length. The slide marks 18 days total at the development step, leaving out QA and launch.
- Correction: Follow the Path is the best method for a button that does nothing, because you trace click, event listener, function, and result. The slides' comparison table lists "button doesn't click" as a Bottom-Up example, but the study guide's practice question 2 correctly answers Follow the Path.
