Type of document: example solution code

In one sentence:
This is the Contact page of the sample Mountain View Coffee Co. site, and it demonstrates the capstone's required form, built so that JavaScript can validate it and show error and success messages.

Main ideas:
1. Head: UTF-8 charset, viewport meta tag, title "Contact Us (separator bar) Mountain View Coffee Co.," a meta description mentioning events, feedback, and the Anytown, Ohio location, an og:title tag, and the shared stylesheet.
2. Header and navigation match the other pages, with the Contact link marked active.
3. Main content, in order:
- Page header section: h1 "Get in Touch" and "We'd love to hear from you."
- Contact info section: three article cards with h3 headings. Visit Us gives the address (123 Main Street, Anytown, Ohio 44146, USA). Call Us gives the phone number and an email link that uses mailto (clicking it opens an email program). Hours lists the weekly schedule.
- Contact form section, h2 "Send Us a Message," with a short intro and the form (described below).
- Other Ways to Connect section (h2): three article cards: Follow Us on Social Media (placeholder links), Visit Us In Person (a link back to the home page), and Email Us Directly (says replies usually come within 24 hours).
- Find Us section (h2): a paragraph about downtown parking and a placeholder image with alt text describing a map. A code comment notes a real site might embed a Google Map here.
4. The form (id contactForm) has the novalidate attribute. That turns off the browser's built-in validation pop-ups so the custom JavaScript can do all the checking and show its own messages.
5. At the top of the form is an empty div with id formMessage. The script fills it with the success message.
6. Each field is wrapped in a div with class form-group. Each has a label whose for attribute matches the input's id, the input itself, and an empty span with class error-message and its own id (for example nameError) where JavaScript writes the error text. The fields are:
- Name: a text input, id name, placeholder "John Doe," marked required. Its label ends with a red asterisk inside a span with class required.
- Email: an email-type input, id email, required.
- Phone: a tel-type input, id phone, labeled "(optional)," not required.
- Reason for Contact: a select dropdown, id subject, required. Its first option has an empty value and reads "Select a reason," followed by five real choices: Feedback about our coffee, Host an event at our cafe, Wholesale or partnership inquiry, Employment opportunity, Other.
- Message: a textarea, id message, 6 rows tall, required.
- Newsletter: a checkbox with its label after it, not required.
- A submit button reading "Send Message."
7. The script tag at the end loads the shared JavaScript, which handles validation for this form.

Key terms:
Form (written <form>) — the container for input controls that a user fills out and submits.
novalidate — a form attribute that turns off the browser's built-in validation so custom scripts can handle it.
Label for and input id — matching values that connect a label to its field, so screen readers announce the label and clicking the label focuses the field.
required — an attribute marking a field as mandatory.
type="email" and type="tel" — input types for email addresses and phone numbers; on phones they bring up a suitable keyboard.
select and option — a dropdown list and its choices.
textarea — a multi-line text box.
checkbox — an on or off choice.
mailto link — a link starting with mailto: that opens the user's email program.
Placeholder attribute — faint example text inside a field that disappears when you type.

What you are asked to do:
Nothing directly; this is the model for the capstone's required form. The spec asks for at least 3 fields with proper types and labels; this form has 6 fields plus a submit button.

Watch out for:
- Every field has a real label tied to it with for and id. Placeholder text is not a substitute for a label.
- The required marker is a visual asterisk; screen readers will say "star," and the required attribute also tells them the field is required.
- The error message spans are not connected to their inputs with aria-describedby and are not live regions, so a screen reader user may not hear the errors automatically when they appear. Adding aria-describedby, or a role of alert on the messages, would improve this in your own form.
- Heads up: alt text must describe what the image really shows. The "map" here is a random placeholder photo from picsum.photos, so its alt text (a map of downtown) is inaccurate; on your site use a real map image or embedded map, or write alt text that matches the actual picture.
- Correction: do not skip heading levels, and use one h1 per page. The contact info cards jump from h1 straight to h3 with no h2, and the page has two h1 elements like the About and Menu pages; in your own page, put an h2 such as "Contact Information" above the cards and keep only one h1.
- The Implementation Guide says the dropdown has 6 options; that count includes the empty "Select a reason" option.
