Type of document: teacher guide (implementation guide)

In one sentence:
This is the teacher's plan for running the html14 capstone over six sessions, with checkpoints, grading steps, answers to common student questions, and ideas for adjusting the project for different students.

Main ideas:
1. The project runs over about three weeks in six sessions, roughly 10 to 12 hours of lab time.
2. Session 1, Project Planning (2 hours): introduce the capstone spec, students pick one of 10 themes or propose their own, fill out the Planning Template, and sketch wireframes on paper for all 4 pages. The teacher must approve the plan before students move on.
3. Session 2, HTML Structure (2 hours): students create 4 HTML files (index, about, services, contact), add semantic structure and meta tags, build a navigation menu on every page, and add placeholder content and images. The example solution HTML is shared as a reference. Checkpoint: the teacher validates all HTML files.
4. Session 3, CSS and Responsive Design (2 hours): students create an external styles.css, add Google Fonts, write mobile-first CSS with media queries, test on desktop, tablet, and phone sizes, and build a hamburger menu. Checkpoint: media queries work.
5. Session 4, JavaScript and Forms (2 hours): students create script.js, validate at least 5 form fields, show error and success messages, optionally add more interactivity, and test the validation with edge cases. Checkpoint: form validation works.
6. Session 5, Testing and Validation (1 hour): validate HTML and CSS with the W3C validators, test in 2 or more browsers, run a Lighthouse audit aiming for 80 or higher, fix accessibility issues, and test all links and forms. Checkpoint: all files pass validation.
7. Session 6, Deployment and Finalization (1 hour): create a public GitHub repository, deploy to GitHub Pages, write a README.md for the repo, complete the Self-Assessment, polish, and submit the URLs. Checkpoint: the site is live.
8. The guide explains which files are for teachers (spec, rubric, README, example solution) and which are for students (planning template, spec, example solution, self-assessment), and when each is used.
9. Example solution breakdown (the Mountain View Coffee Co. site). Home page: navigation to all 4 pages, a hero section with a call-to-action button, feature cards in a CSS grid, product showcase, testimonials, and footer. About page: company story, 4 team profiles, mission, core values, a timeline, images with alt text. Menu page: categories for espresso, cold drinks, pastries, and specialty drinks, plus the required table (a coffee comparison guide with columns Drink Name, Espresso, Milk, Foam, Strength, Best For, and 6 rows). Contact page: info cards, the required form with name (text), email (email type), phone (tel type), a subject dropdown, a message textarea, a newsletter checkbox, and a submit button, plus a map placeholder image.
10. The stylesheet uses CSS variables, media queries at max-width 768 pixels (tablet) and max-width 480 pixels (mobile), a sticky header with hamburger menu, grid layouts, Google Fonts Montserrat and Merriweather, and a palette of brown (hex 8B4513), gold (hex D4AF37), and cream (hex E8DCC8).
11. The script has five validation functions: validateName (2 or more characters), validateEmail (pattern check), validatePhone (10 or more digits, optional), validateSubject (dropdown required), and validateMessage (10 or more characters). It also does real-time checks on blur, a success message and form reset, the hamburger toggle, smooth scrolling, and Escape-key handling.
12. Suggested teacher scripts: introduce the project as something students can show colleges and employers, present the coffee shop only as an example of structure, and use a short checkpoint statement at each session (plan before code; clean valid HTML with working navigation; professional design tested on real devices; working form validation that shows DOM skills; everything validated and tested; site live on GitHub Pages).
13. Grading workflow: students submit a GitHub Pages URL, a public repository URL, the completed Self-Assessment, and the completed Planning Template. The teacher checklist is: HTML passes W3C with 0 errors; CSS passes W3C with 0 errors; live on GitHub Pages; 4 or more pages with navigation; responsive design tested on mobile; form validation works; a table with data; alt text on images; semantic HTML throughout; custom CSS, not only Bootstrap; JavaScript interactivity; SEO basics (title and meta description); accessibility basics (contrast and keyboard navigation); self-assessment done; README in the repo.
14. Scoring uses the rubric's 7 categories, each with five levels: Excellent, Good, Satisfactory, Needs Work, Missing. Extra credit is allowed for advanced features.
15. Common student questions: Bootstrap is allowed but only as a supplement to your own custom CSS. You do not have to use the coffee shop theme. The form does not need to send email; it only needs to validate and show messages. Write real content, such as 2 to 3 paragraphs on the About page. If stuck, study the commented example solution. Validation errors cost rubric points, so use validator.w3.org; most errors are simple, like missing closing tags or typos.
16. Success indicators: students can explain why planning comes first, use semantic tags, write responsive CSS, validate forms, test and debug with browser tools, deploy with GitHub Pages, explain and apply accessibility basics, and reflect on their learning.
17. Differentiation. Advanced students: multi-step form wizard, saving form data in local storage, image gallery or carousel, dark mode toggle, CSS Grid layouts, scroll animations. Struggling students: an HTML template, pre-written CSS variables, a 3-field form instead of 5, a 3-column table instead of 6, a peer mentor, extra testing time. Interest-based themes: portfolio (artist), band site (musician), sports team (athlete), gaming community (gamer), small business (entrepreneur), nonprofit (activist).
18. Timing: can be squeezed into 5 sessions or stretched to 8 to 10, and is meant for 16 to 18 year olds with 10 weeks of earlier learning.

Key terms:
Checkpoint — a point where the teacher checks work before students continue.
Wireframe — a rough layout sketch of a page.
W3C Validator — the official online tool that checks HTML (validator.w3.org) or CSS for errors.
Lighthouse — a Chrome DevTools audit that scores performance, accessibility, best practices, and SEO.
GitHub Pages — free hosting that publishes a website straight from a GitHub repository.
Edge case — an unusual input used to test validation, such as an empty field or a bad email.
Differentiation — changing a task to fit students of different skill levels or interests.
Local storage — browser storage that keeps data after the page is closed (an advanced extension idea).

What you are asked to do:
This guide is for the teacher, but it states what students submit in Session 6:
1. GitHub Pages URL (the live website).
2. GitHub repository URL (public).
3. The completed html14_SelfAssessment.md.
4. The completed html14_PlanningTemplate.md as proof of planning.

Watch out for:
- Validation errors lead to rubric deductions, so validate early and often.
- Bootstrap alone is not enough; custom CSS must be your main stylesheet.
- Correction: build and validate at least 5 form fields, which satisfies both documents. This guide asks for 5 validated fields, while the Capstone Spec asks for only 3 input fields and fewer validation rules.
- Heads up: the Capstone Spec expects the fourth page to be named services.html, so use that name. The example solution calls its fourth page menu.html because it is a coffee shop, but that page plays the same role.
- Correction: the project is six sessions, about 10 to 12 hours of lab time; how many calendar weeks that takes depends on the class schedule. The teacher script says "5-6 weeks" while the session plan describes about 3 weeks, so the real due date is Mr. McMaster's call.
- Correction: mobile-first means base styles for small screens, then min-width media queries for bigger screens, and the course requires mobile-first. The example stylesheet uses max-width queries to shrink a desktop layout, which is desktop-first, even though the guide calls it mobile-first.
