Main ideas:

Section 1, Responsive design and CSS layout:
1. Responsive design means the layout and content adapt to any screen size or device (competency 6.5.13).
2. The viewport meta tag tells phones to use the device's real width. Without it, phones show a zoomed-out desktop page.
Code: <meta name="viewport" content="width=device-width, initial-scale=1.0">
This sets the page width to the device width at normal zoom.
3. A media query is CSS that applies only when a condition is true.
Code: @media (min-width: 768px) { ... }
Rules inside apply only on screens at least 768 pixels wide.
4. Mobile-first means the base styles target phones, and min-width media queries add styles as screens get larger.
5. A breakpoint is a screen width where the layout changes. The common ones are 768 pixels (tablet) and 1024 pixels (desktop).
6. Flexbox is one-dimensional layout: a row OR a column. Key properties: display: flex, justify-content (spacing on the main axis), align-items (alignment on the cross axis), flex-wrap, and gap.
7. CSS Grid is two-dimensional layout: rows AND columns at once, using display: grid, grid-template-columns and gap. You only need to recognize it.
8. The responsive image rule is img with max-width: 100% and height: auto, so images never overflow and keep their proportions.
9. Competency 2.7.2, ways to present data: know all four delivery options, which are a responsive website, a mobile app, a desktop app, and a web application.
10. The mobile-first skeleton: a container that is display: flex with flex-direction: column and a gap of 1rem, plus a min-width 768px media query that switches flex-direction to row.
11. Framework note: a CSS framework (Bootstrap is the famous one) is pre-written CSS with a grid system and ready-made components such as navbars, cards and alerts. Know what a framework is and why teams use one: speed and consistency, at the cost of control. You do not need its class names.

Section 2, HTML forms:
1. Ten terms: form (collects user input), action (URL where the data is sent), method (GET or POST), input (the control for text, email, checkbox, radio and so on), label (text tied to a control for accessibility), fieldset (groups related controls), legend (title for a fieldset, improves accessibility), radio button (single select; only one in a group), checkbox (multi select), submit button (sends the data to the server).
2. GET versus POST, feature by feature:
- Where the data goes: GET in the URL query string; POST in the message body.
- Visibility: GET is visible to the user; POST is hidden.
- Size limit: GET about 2000 characters; POST has no practical limit.
- Bookmarkable: GET yes; POST no.
- Caching: GET is often cached; POST is not cached by default.
- Security: GET is less secure because the data is visible; POST is more secure.
- Typical use: GET for searches and filters; POST for logins and sensitive data.
- Idempotent (safe to repeat): GET yes; POST no, because it can have side effects.
3. Radio versus checkbox: radio is one choice, checkbox is multiple. Radios must share the same name; the guide says checkbox names can differ. Radio is for either-or choices, checkbox for several selections. Written as input type="radio" and input type="checkbox".
4. The complete example form uses action="process.php", method="POST" and name="contactForm". It has a Contact Information fieldset with required full name and email fields, and a Preferences fieldset with a phone or email radio pair (name contact) and a sports and music checkbox pair (name interests), each input with its own label, followed by Submit and Clear (reset) buttons.
5. Input types to know: text (single line), email (validates email), password (masked), number (numeric with a spinner), tel, url, date (date picker), checkbox, radio, file (file upload), submit, reset, button (generic), hidden (not displayed).
6. Why use fieldset and legend: they group related controls, screen readers announce the group name, they improve visual organization, and they give better form semantics. The example is a Shipping Address fieldset containing Street and City.

Section 3, SEO and accessibility:
1. Twelve terms: SEO (search engine optimization, making sites visible in search results); title tag (page title shown in the browser tab and search results); meta description (page summary shown in search results); heading hierarchy (h1, h2, h3 structure showing importance); keyword (word or phrase people search for); alt text (text description of an image); ADA (Americans with Disabilities Act, a legal requirement); WCAG (Web Content Accessibility Guidelines, the standards); accessibility (usable by people with disabilities); screen reader (software that reads the page aloud); ARIA (Accessible Rich Internet Applications, attributes that add accessibility information); contrast ratio (difference in brightness between text and background).
2. SEO checklist before publishing:
- Title: unique, 50 to 60 characters, includes the main keyword.
- Meta description: 150 to 160 characters, compelling, includes the keyword.
- One h1 per page stating the main topic.
- h2 and h3 in proper hierarchy describing sections.
- Keywords placed naturally in the title, headings and first 100 words.
- Descriptive alt text on all images.
- Internal links to related pages.
- Mobile friendly (responsive).
- Fast: optimized images, minified CSS and JavaScript.
- Descriptive URLs using hyphens, for example example.com/web-design-tips.
The example SEO page has a keyword-rich title, a meta description, one h1, h2 section headings, and an image with descriptive alt text.
3. Accessibility checklist for WCAG AA:
- Color contrast at least 4.5 to 1 for text and 3 to 1 for graphics.
- Everything works by keyboard.
- Meaningful images have descriptive alt text.
- Every input has a label.
- Proper h1 to h6 structure.
- A skip-to-content link at the top.
- ARIA labels for icon buttons, using aria-label and aria-describedby.
- Clear, specific error messages linked to their fields.
- Captions for video and transcripts for audio.
- Visible focus indicators.
- No keyboard traps: you can move into and out of every element.
- Page language set on the html tag.
4. The accessible form example connects a username input to a help text (3 to 20 characters, letters and numbers only) using aria-describedby, and gives the Sign In button an aria-label of "Sign in to account".
Code: <input id="username" aria-describedby="username-help">
aria-describedby points to the id of the element holding extra help text, so a screen reader reads that help after the label.
5. WCAG levels: A is minimal, the foundation. AA is the industry standard and what most laws require. AAA is enhanced, best-in-class.
6. Where SEO and accessibility overlap: alt text helps screen readers and image search; heading hierarchy helps both; both need semantic markup; keyboard navigation and mobile friendliness help SEO; fast loading reduces cognitive load and is a ranking factor; clear writing helps both readers and keywords.

Section 4, protocols and deployment:
1. Terms: HTTP (HyperText Transfer Protocol, unsecured); HTTPS (HTTP Secure, encrypted); FTP (File Transfer Protocol, for uploading files, now replaced by SFTP); TCP/IP (Transmission Control Protocol and Internet Protocol, the foundation of the internet); DNS (Domain Name System, turns domain names into IP addresses); SSL and TLS (Secure Sockets Layer and Transport Layer Security, the encryption); certificate (digital file proving a site's identity for HTTPS); deployment (publishing a site to a live server).
2. Protocol status table in words: HTTP is for web pages, has no security, and is listed as deprecated. HTTPS is encrypted with SSL or TLS and required now. FTP transfers files with no security and is legacy. SFTP (SSH File Transfer) is encrypted with SSH and current. TCP/IP is the internet foundation, not encrypted, always used. DNS does domain to IP lookup, not encrypted, always used. SSL is encryption that has been replaced by TLS. TLS is the current encryption standard.
3. HTTP sends plain text anyone can read; HTTPS encrypts using an SSL/TLS certificate. Every site must use HTTPS for security, SEO (Google ranks HTTPS higher), trust (the lock icon) and compliance (privacy laws).
4. DNS converts a name like example.com into an IP address like 192.0.2.1. It is like the internet's phone book, takes a few seconds, then is cached locally, and is not encrypted.
5. TCP/IP: TCP makes sure data arrives correctly and in order; IP routes data between computers. HTTP, HTTPS, FTP and email all run on it.
6. Git commands:
- Set up once: git config --global user.name and git config --global user.email.
- Start: git init creates a new repository; git clone copies an existing one from a URL.
- Change: git status shows what changed; git add followed by a file name stages one file; git add followed by a period stages everything; git commit -m followed by a message saves the changes locally.
- Push: git remote add origin followed by a URL connects to GitHub; git push -u origin main pushes the first time; plain git push afterwards.
- Pull: git pull downloads and merges the latest changes; git fetch downloads without merging.
- History: git log shows commit history; git diff shows unstaged changes; git diff --staged shows staged changes.
7. GitHub Pages deployment for static sites:
- Create a repository. Name it username.github.io for a user site, or any name for a project site. The guide says to add a README and a .gitignore for Node, then clone it to your computer.
- Copy in index.html, CSS and JavaScript, then git add and git commit.
- Push with git push -u origin main.
- In the repository go to Settings, then Pages; under Build and deployment choose Deploy from a branch, pick main (or gh-pages), and save.
- The site appears at https://username.github.io for a user site or https://username.github.io/repo-name for a project site, after 1 to 2 minutes. Example: user jsmith with repo portfolio is at jsmith.github.io/portfolio.

Section 5, troubleshooting and QA:
1. Terms: bug (error or unexpected behavior); debugging (finding and fixing bugs); breakpoint (here, a point in code where execution pauses so you can inspect it); console (browser tool showing errors and logs); inspector (browser tool showing live HTML and CSS); test case (a specific scenario to check a feature); QA (quality assurance, testing before release); regression (a bug that comes back after being fixed).
2. The four troubleshooting methods:
- Top-down, start high and go low: check the overall structure, HTML validity first, then CSS, then JavaScript. Best for structure and layout problems. Example, a missing button: check that the button tag is there, then whether CSS sets display: none, then whether JavaScript hides it.
- Bottom-up, start low and go high: start with the error message, find the function that failed, then trace what called it. Best for JavaScript errors. Example, a TypeError: find the exact line in the console, read the message, check the variable exists, check the function that creates it.
- Follow the path, trace the data: start at the user action (a click or submission), follow the data through each handler and change, check the server or database, then trace back to the output. Best for data flow problems. Example, a form that does not submit: check in order that the submit event fires, validation passes, the request goes out (Network tab), and the server responds.
- Spot the differences, compare: find a working and a broken version, use git diff and the inspector to compare, look at recent changes. Best when something just broke. Example, a layout broke after an update: git diff, compare CSS in the inspector, check applied styles, revert recent changes to test.
3. Browser DevTools tabs: Console shows errors and runs JavaScript; Inspector (Elements) shows the HTML and lets you edit CSS live; Network shows HTTP requests, timing and failures; Sources lets you set breakpoints and step through JavaScript; Application shows localStorage, cookies and cache.
4. External tools: the W3C HTML Validator at validator.w3.org, the W3C CSS Validator at jigsaw.w3.org/css-validator, git diff for exact changes, git log for history.
5. Test case template fields: test case ID (for example TC-001), title, precondition, numbered steps, expected result, actual result (filled in during testing), status PASS or FAIL, and notes. The example tests logging in with a valid email and password and expects to land on the dashboard.
6. QA checklist:
- Functionality: buttons and links work, forms submit, navigation, search and filters work, no broken links.
- Compatibility: Chrome, Firefox, Safari, Edge, iOS and Android.
- Responsiveness: mobile under 576 pixels, tablet at 768, desktop at 992 and up; no overlapping elements; readable text; images scale.
- Accessibility: keyboard navigation, sufficient contrast, alt text, form labels, clear errors, visible focus.
- Performance: loads in under 3 seconds, no broken images, no console errors, optimized files, smooth scrolling, no lag.

Section 6, business, ethics and professional skills:
1. Copyright: automatic protection of original creative work, lasting the author's life plus 70 years in the US, covering text, code, images, music and video. Do not use without permission. Written with the copyright symbol, year and name.
2. Trademarks protect brand names and logos; the registered symbol (R in a circle) requires registration; examples are Google, Apple and Nike. Do not use company logos without permission.
3. Fair use is a limited exception allowing use for education, criticism, commentary and parody. It is not blanket permission; it is decided case by case using the purpose, the amount used, and the effect on the original's value. Safer to use Creative Commons or licensed content.
4. Licenses: All Rights Reserved is the default and allows nothing. Creative Commons lets the author allow specific uses: CC-BY requires attribution; CC-BY-SA requires attribution and sharing under the same license; CC-BY-NC requires attribution and non-commercial use only; CC0 is public domain, free to use. Open source licenses such as MIT, GPL and Apache allow free use of code. Royalty-free means pay once and use indefinitely.
5. Best practices: cite sources; use Creative Commons image sites such as Unsplash and Pexels; use licensed fonts such as Google Fonts; use open-source code correctly; never screenshot copyrighted content; when unsure, ask permission.
6. ADA: the Americans with Disabilities Act of 1990 is a federal law requiring equal access, applied to websites under Title III. It is the business's responsibility, not optional. Lawsuits are increasing, the Department of Justice enforces it, settlements average 50,000 dollars or more, and it harms reputation.
7. What must be accessible: images (alt text), videos (captions and transcripts), forms (labels and clear errors), buttons (keyboard accessible, clearly labeled), color (never the only way to convey information), and navigation (logical and keyboard friendly).
8. Who benefits: blind and low-vision users (screen readers), deaf and hard-of-hearing users (captions), people with motor disabilities (keyboard navigation), people with cognitive disabilities (clear language), and everyone.
9. WCAG levels in more detail: A is the bare minimum, with many features still missing. AA is the industry target that most laws reference, requiring 4.5 to 1 contrast. AAA is the highest, requiring 7 to 1 contrast; it is hard and expensive and not required by law. Bottom line: aim for AA.
10. Portfolio: show your 3 to 5 best projects with screenshots, descriptions and tools used, link to live sites on GitHub Pages, show variety, update regularly, quality over quantity.
11. Resume: one page (two only if very experienced), relevant skills, projects with descriptions, education and certifications, contact information including email, GitHub and LinkedIn, tailored to the job, no typos.
12. Feedback and growth: accept constructive criticism gracefully, ask how to improve, act on feedback, learn from mistakes, share what you learn, help others.
13. Professionalism: reply to messages within 24 hours, meet deadlines, report status regularly, ask clarifying questions, be honest about your abilities, admit what you do not know and offer to learn, dress appropriately for interviews, and use a proper handshake and eye contact.
14. Project management:
- Scope: what is included and what is explicitly excluded. Scope creep means adding features beyond the original plan. Define scope up front and record it in the design brief.
- Stakeholders: anyone affected by or interested in the project, such as the client or owner, end users, team members, and managers. Get their buy-in early.
- Timeline: start and end dates, milestone dates, deliverable deadlines, buffer time for unknowns, updated as work goes on.
- Milestones: major checkpoints such as design approval, development start and testing; they track progress and are worth celebrating.
- Critical path: the chain of tasks that sets the shortest possible project length. Any delay on it delays the whole project; tasks off the path have slack time. Example: design, then HTML, then CSS, then testing, then deployment.
- Six phases: planning (scope, timeline, resources), design (wireframes, mockups, approval), development (coding), testing (QA and bug fixes), deployment (launch), maintenance (monitoring, fixes, updates).
15. Design brief components, in order: project title with version and date; 1 client or stakeholder and decision-maker; 2 project overview, what and why; 3 goals and objectives and how success is measured; 4 target audience, demographics and needs; 5 scope, included, not included, features; 6 deliverables and their format; 7 timeline and milestones; 8 budget if applicable, with cost by phase; 9 constraints and assumptions, including technical and browser or device requirements; 10 success criteria and metrics.

Key terms:
viewport meta tag — makes phones use their true screen width.
mobile-first — base styles for phones, min-width queries for bigger screens.
main axis and cross axis — flexbox directions controlled by justify-content and align-items.
idempotent — safe to repeat without extra side effects (true of GET).
aria-describedby — links a control to an element holding extra help text.
aria-label — gives an element an accessible name, useful for icon-only buttons.
skip link — a link at the top that jumps past navigation to the main content.
keyboard trap — a spot where keyboard focus gets stuck.
SFTP — secure, SSH-encrypted file transfer.
TLS — current encryption standard behind HTTPS, replacing SSL.
regression — an old bug returning.
critical path — the task chain that determines the minimum project length.
scope creep — features added beyond the agreed plan.
fair use — limited, case-by-case exception to copyright.
CC0 — Creative Commons public domain dedication.

Watch out for:
- The word breakpoint has two meanings in this guide: a screen width in CSS (Section 1) and a pause point in JavaScript debugging (Section 5).
- Fair use is not blanket permission; it is judged case by case, so licensed or Creative Commons content is the safer choice.
- WCAG AA is the usual legal target; AAA is not legally required.
- A git commit only saves locally; you must push to reach GitHub.
- Correction: radio buttons in one group must share the same name, and checkboxes in a group conventionally share one name too so their values submit together; that is what html08 teaches and the safe exam answer. This guide says checkbox names "can differ", which also works but is not the taught way.
- Correction: a label names one control, so its for must match an existing input's id, and a group of radio buttons or checkboxes is named with a fieldset and legend. In the example form the "Interests:" label's for="interests" matches no input and the "Contact Method:" label has no for, so each group should be wrapped in a fieldset with a legend instead.
- Correction: HTTP is not deprecated; it still works, but browsers mark HTTP pages "Not secure", so always use HTTPS. The guide's protocol table wrongly lists HTTP as "Deprecated".
- Heads up: breakpoints are design choices, not fixed rules. Learn 768 pixels (tablet) and 1024 pixels (desktop) from Section 1 as the course numbers; the QA checklist's 576, 768 and 992 are Bootstrap's sm, md and lg breakpoints left over from the Bootstrap version.
- Correction: outside notes or references are not allowed during a certification exam, so use this guide before the exam, not during it. The final reminders' "bookmark this guide for reference during exam" is wrong.
- Heads up: Top 10 items 6 (GitHub Desktop) and 9 (semantic HTML) are not covered in any section of this guide, so review commit-then-push in GitHub Desktop from html10 and semantic tags from html02. The git commands in Section 4 are the command-line version, which the html10 Unit Guide says is not the class workflow.
